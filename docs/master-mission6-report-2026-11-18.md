## What was built

**Host reward engine** (`core/atlas_rewards.py`, 1,228 lines, stdlib-only): the 75/25 reward engine in simulation.
- Inputs: verified accepted shares (difficulty-weighted, pool-confirmed or local-test-verified) + confirmed pool reward batches only. Local hashrate is NOT evidence; estimated hashrate is never paid from.
- Fees: gross → pool fee (bps from `config/pool-rewards.json`: MoneroOcean 0, SupportXMR 60, P2Pool 0; floored, remainder stays in net) → net → split. Payout tx fees are NOT deducted at split time (per config, at payout time; none in M6).
- Split: integer piconero only, floats forbidden. ATLAS = `net*25//100` (floored), users get `net − ATLAS`. Per-user allocation by largest-remainder method (ties → lowest user_id), so Σ allocations = users_total exactly, zero dust.
- Attribution: share → worker → user by FK; weight = `COALESCE(difficulty,1)`. NULL-difficulty shares count weight 1 and are flagged; NULL-`external_id` pool shares are excluded (no dedupe key, no credit) and counted.
- Ledger: append-only with SHA-256 hash chain (genesis `prev_hash` = 64 zeros; canonical sorted-key JSON payload; deterministic order fee → atlas_share → referral_reward → user_allocation). Exact entry fields; sign convention defined; corrections only via `reversal` entries; 5-step `verify_chain()`. Balances derived by `SUM`, never stored.
- Double-credit prevention (three layers): the coordinator's existing share dedupe; batch exactly-once via `UNIQUE(pool_name, source_ref)` + `UNIQUE(share_id)` link table in a single transaction; payout idempotency keys.
- Referrals: 5% (500 bps, config parameter) of the referred user's allocation per cycle, from the ATLAS 25% only, direct only, no self-referral, only when the referred user earned > 0. Cap proof: max 3.75% of net < 25%, so the cap never binds. Zero referrals today → honestly 0.
- Simulation: simulation batches settle while the stop is ON (documented exemption — they move no real value); real-mode batches are REFUSED while the stop is ON or mode is `simulation-only`. All simulation figures marked in DB, ledger, and UI. Simulation runs on a temp DB; the live DB gets zero ledger rows from M6. Gate 4 (a real payout) is a hard gate.
- Cycles: one cycle = one batch; opens on record (CLI), closes on settle in one transaction. The engine rides the existing 10-min coordinator pass as a guarded no-op-when-nothing-due sub-step (no new cron, never fails the pass) plus an on-demand CLI (`record-batch`, `settle`, `status`, `verify-chain`, `export`). Zero-weight or zero-gross batches are HELD, never auto-allocated to ATLAS.
- Any payout-shaped call is refused with a logged refusal (Gate 4 closed).
