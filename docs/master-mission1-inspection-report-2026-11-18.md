## Executive summary

ATLAS today is a **monitoring-only system**, and it is honest about that. There is no mining platform: no user accounts, no worker registry, no pool client, no share accounting, no reward engine, no payout system, no browser or desktop miner, and no Mining tab. What does exist is a solid, well-tested foundation — a metrics daemon, a decision audit log, a 15-test diagnostics suite, a tracked refresh pipeline, a provenance-tagged dashboard, and a reusable worker/capacity ledger — on which the mining platform can be built. The build is large: essentially everything in sections 3–20 of the master mission must be created from scratch.

The single most important finding is the **browser-mining verdict: IMPRACTICAL as an earner.** Browser RandomX mining is real and demonstrable, but a laptop browser tab earns about **$0.008/day gross** and loses about **$0.10–0.13/day net** after electricity — roughly an order of magnitude uneconomical. With the planned 75/25 split, a user keeps $0.006/day, about 167 worker-days to earn $1. The browser miner can only be honestly framed as a participation/demo feature, never as a revenue stream. The desktop miner (native XMRig) is 30–80× faster and is the only path that approaches breakeven — and even it barely breaks even at average electricity prices.

**Gemini status:** Gemini was attempted for the research lane (4 calls, gemini-3.5-flash) and returned nothing usable — HTTP 503 overload twice, then 60 s read timeouts twice, consistent with the exhausted quota noted today. Per the standing rule, retries stopped and the work continued with independent web research only. Every number in the feasibility section is therefore web-sourced, not Gemini-sourced. There is no Gemini-vs-search disagreement to flag, because Gemini said nothing at all.

**Safety state (verified live, unchanged):** emergency stop ACTIVE, mining DISABLED, trading PAPER ONLY, eligible capital $0. No wallets, keys, or seed material exist on the host. All financial figures in this report are design/projection, never real earnings. Realized mining revenue is $0.

### 2.2 The backend — `~/workspace/atlas/core/`
- **`atlas_monitor.py` (13,313 B) — the daemon.** Infinite loop, 60 s cycle. Collects real host metrics only from `/proc` (CPU from `/proc/stat`, memory from `/proc/meminfo`, load averages, disk usage, network bytes from `/proc/net/dev`). Writes each row to SQLite (`INSERT OR REPLACE INTO metrics`) and publishes `data/snapshot.json` via atomic write (`.tmp` → `os.replace`). Timestamped logging to `logs/monitor.log` with 1 MB rotation (one backup); logging failures are swallowed so logging never breaks monitoring. `check_integrity()` runs read-only `PRAGMA integrity_check` (URI `mode=ro` first). `recover_database()`: a locked DB is treated as transient (sleep 1 s, retry); a corrupt DB is quarantined (renamed to `atlas-corrupt-<UTC>-<pid>.db`, journal/WAL/SHM moved alongside, never deleted/overwritten), then `create_fresh_db()` verifies integrity plus a rolled-back test write before writes resume. `load_config()` re-reads `config/atlas.json` every cycle; the emergency stop is read-only for the daemon. The daemon never crashes on a DB error. Reusable as the template for a worker-health heartbeat and a pool-stats collector; the atomic snapshot write and the "never crash, degrade gracefully" discipline are the right model for any new daemon. Cannot be reused as-is: it collects host metrics only — no hashrate, no shares, no pool data, no worker identity; `gpu` is hardcoded `None`; no network calls at all.
- **`atlas_core.py` (3,777 B) — coordinator skeleton.** CLI with two commands: `status` (prints config state + last snapshot + metrics count + last 5 decisions) and `decide` (one coordination pass). `load_config()` crashes on bad config (unlike the monitor, no fallback). `log_decision()` logs every decision with a reason string. `decide()` enforces the hard rules: stop ON → `hold-all-live-activity`; mining disabled → `stay-disabled`; trading disabled → `stay-paper-only`; CPU over `limits.max_cpu_pct` (50) → `throttle-background-work`. Reusable: the decision-log pattern (reasoned, timestamped rows) as the audit trail for coordinator actions (worker admission, pool switch, payout approval), and the `status` CLI pattern for an operator CLI. Cannot be reused as-is: this is a policy-enforcement stub, not a coordinator — no worker registry, no job dispatch, no pool interaction, no scheduling beyond a single manual pass, no auth, no queue. It is ~110 lines; the real mining coordinator must be built, using this only as its shell/audit pattern.
- **`diagnostics.py` (15,958 B) — 15-test suite.** Each test records PASS/FAIL/NOT TESTED with evidence, writes `data/diagnostics.json`, exit 0 = all pass, 1 = any fail, 2 = any not-tested. Tests: 01 Python services; 02 daemon running (pgrep bracket trick); 03 snapshot freshness; 04 disk/net; 05 DB integrity + 3 tables; 06 DB persistence; 07 coordinator `decide` logs a new decision; 08 decision logging (reasons present); 09 emergency stop (config + snapshot + mining/trading disabled + hold decision); 10 service restart (SIGTERM → restart → fresh snapshot ≤15 s); 11 auto-recovery (`recover.sh` after kill → daemon back ≤20 s); 12 deployment persistence; 13 resource consumption (RSS <50 MB, lifetime CPU <5%); 14 network (CoinGecko, MoneroOcean, blockchain.info all 200 — note: ≥2/3 = FAIL "partial"); 15 security (walk for `.pem`/`.key`/`id_rsa`/seed files, PEM armor + `xprv` regex scan of code, pgrep for miner processes, config not world-writable, stop/mining/trading assertions). Reusable: the harness shape (`record()` + JSON + exit codes) and several individual tests (02, 05, 09, 13, 15) are directly extensible — e.g. a test asserting "no miner process unless authorized worker", "pool API reachable", "reward ledger balances". Test 14 already probes the exact pool endpoints the platform needs. Limits: tests are host-local and single-node; no multi-worker, pool, wallet, or payout coverage. Test 14 is flaky under memory pressure (Mission 1.1: transient fail, all 200 on re-check 2 min later). Tests 10/11 restart the daemon (destructive to a running system — fine for diagnostics, not for a live coordinator).
- **`recover.sh` (610 B, executable).** `flock -n` on `data/recover.lock` (concurrent runs exit silently, no duplicate daemons); if pgrep finds nothing, `nohup python3 core/atlas_monitor.py > logs/monitor.log 2>&1 &` and appends to `logs/recover.log`. Idempotent, safe from cron/systemd/by hand. Reusable verbatim for any new daemon. Known flaws (Mission 1.1 §7.3): it truncates `logs/monitor.log` on every restart (`>` redirect — only the rotated `.1` survives); and a command line containing the literal string `atlas_monitor.py` defeats the pgrep check (the Mission 1.1 deploy incident left the daemon down ~2 min). Any new service script should use `>>` append and the bracket trick.
- **`config/atlas.json` (version `0.1.0-stage2`).** `emergency_stop: true`; `host_role: "worker-1-bootstrap"`; `mining: {enabled: false, cpu_candidate: "monero-randomx", status: "design-only", reason: "No authorization to mine on shared host infrastructure; no GPU; shared 1.5 CPU cell"}`; `trading: {enabled: false, mode: "paper-only", eligible_capital_usd: 0, futures/leverage/margin/options: false}`; `limits: {max_cpu_pct: 50, max_mem_pct: 70, max_temp_c: null, note: "Limits are immutable without user authorization"}`; `monitor_interval_s: 60`; `blockchain_apis: {blockchain_info: "verified-200", coingecko: "verified-200", mempool_space: "unreachable-from-this-host", moneroocean: "verified-200"}`. Reusable: the config-as-single-source-of-truth pattern, with the emergency stop read every cycle, is the right safety backbone — the platform must keep a kill-switch read on every loop, never cached. The `blockchain_apis` reachability map is already the seed of a pool/endpoint registry. Limits: flat file, no per-user/per-worker sections, no secrets handling (correctly — none exist), no pool credentials, no wallet addresses, no payout config. Any multi-user config needs a new structure; do not overload this file.
- **Hard constraints of the codebase:** plain Python 3.11+ stdlib + SQLite + JSON only — no third-party dependencies anywhere. Single-host, single-node: one daemon, one SQLite file, one JSON snapshot, local `/proc` reads. No networking in the daemon at all; the only HTTP in the codebase is `diagnostics.py` test 14 and the artifact-side Command Center ingestion. Portable by copying `~/workspace/atlas` (migration = copy tree + Python 3.11+ + `recover.sh` + `diagnostics.py` 15/15), but processes do not survive VM replacement — restore is via a cron watchdog (5 min) or a systemd user unit. No concurrency design: single-threaded loop, `sqlite3` with 5 s timeouts, no locking beyond `recover.sh`'s flock, no queue, no API server, no HTTP listener.

### 2.3 The database — `~/workspace/atlas/data/atlas.db`
- Healthy and tiny (36,864 bytes, 9 pages). Schema: `metrics(ts INTEGER PRIMARY KEY, cpu, mem_used_pct, load1/5/15, disk_used_pct, net_rx/tx_bytes)` — host health time-series only, ~1 row/min (177 rows, span 2026-11-17 23:24 → 2026-11-18 02:24, ~1,440 rows/day, no retention/pruning policy); `decisions(id, ts, dept, decision, reason)` — 28 rows, evenly split core/mining/scheduler/trading (7 each), the audit trail for the safety holds (latest: `hold-all-live-activity`, `stay-disabled`, `stay-paper-only`, `throttle-background-work` at CPU 56.08% over the 50% cap); `events(id, ts, kind, message)` — 16 rows, all `kind='startup'` (no error/warning/alert kinds exist yet). Plus internal `sqlite_sequence`.
- The snapshot (`data/snapshot.json`, 385 bytes) is a single flat JSON object whose `ts` exactly matches the latest `metrics` row — snapshot and DB are in sync.
- Reusable unchanged: `metrics` (host health for the coordinator/dashboard — add mining-specific stats separately, do not overload it); `decisions` (already the right shape for coordinator/reward-engine audit decisions — add new `dept` values like `rewards`, `payouts`); `events` (generic event log; new `kind` values like `share_accepted`, `payout`, `worker_connected` fit naturally). Timestamps are Unix epoch integers across all three tables and the snapshot — keep that convention for new tables.

## 4. Browser RandomX feasibility — honest verdict

**Verdict: IMPRACTICAL as an earner. Browser RandomX mining is real and technically demonstrable, but uneconomical by roughly an order of magnitude; defensible only as a participation/demo feature, never as a revenue stream.**

### 4.1 The numbers (all web-verified 2026-11-18; Gemini contributed nothing — see Executive summary)

**Dataset and memory (confirmed by multiple sources):** RandomX full/fast mode needs a **~2 GB dataset** plus **2 MB scratchpad per thread** (256 MB cache in light mode). WASM32 linear memory caps at **4 GiB total** for module + dataset + heap, so the dataset alone consumes half the address space. Practical consequences: the dataset must be generated once (minutes) and cached between visits (VoltMiner caches it in OPFS); light mode avoids the dataset but is far slower.

**Measured browser hashrates (real projects, 2026):**

| Setup | Hashrate | Source |
|---|---|---|
| Laptop browser miner, whole tab | ~200 H/s | Monerica, Oct 2026 |
| 32-thread desktop browser, whole tab | ~850 H/s (~27 H/s/thread) | Monerica, Oct 2026 |
| Browser WASM, per core, light mode (no dataset) | ~8.8 H/s/core; phone 2–5 H/s/core | SoapBox pool, measured vs official RandomX test vector |
| Native XMRig, per core | 450–700 H/s/core | SoapBox (same page) |
| Native laptop (XMRig/P2Pool) | ~6,300 H/s vs 200 H/s browser on same laptop | Monerica — ~30× gap |
| Ryzen 7 5800X, native | 10.0–12.4 kH/s (XMRig benchmark 12,445 H/s) | XMRig benchmark, Kryptex, asicprofit |

**The gap:** the browser is **~25–50× slower per thread than native in fast-mode WASM**, and **~50–80× slower in light mode**. Monerica: "in public WebAssembly tests, a browser reached roughly a quarter of native speed at best, and around half of even RandomX's slow 'light' mode. RandomX's own authors describe web mining as impractical." A whole browser tab on a 32-thread desktop (850 H/s) is ~12–15× slower than one Ryzen 7 5800X running natively, and ~7% of it.

**What limits it:**
- **No AES-NI in WASM** — AES must be emulated in software; RandomX is AES-heavy.
- **No JIT random-code execution** — native XMRig JIT-compiles each random program; WASM ports (WebRandomX, RandomX-bonanza) emulate or use a slower JIT; WASM has **no `fesetround`**, so floating-point rounding modes must be emulated in a variable. VoltMiner's October 2026 blog shows this emulation bug silently produced valid-looking but wrong hashes — every share rejected.
- **No huge pages** in a browser — native gains 20–50% from huge pages; browsers cannot do this.
- **Threads need SharedArrayBuffer**, which needs **COOP/COEP cross-origin-isolation headers + HTTPS**; without them the miner falls back to single-threaded. Safari/iOS is the weak case.
- **Tab throttling/suspension** — hidden/background tabs are throttled or stopped ("A hidden tab stops hashing" — VoltMiner; "Mining stops if you close or background the tab" — SoapBox). Sustained 24/7 mining from a tab is not a real operating mode.
- **Browser/antivirus blocking** — Firefox 69+ blocks known cryptomining scripts by default; Brave and AV tools block them; the Chrome Web Store bans mining extensions. Any ATLAS browser miner must survive blocklists and the cryptojacking reputation.

### 4.2 WebGPU and RandomX: NO, it does not help

RandomX is deliberately the anti-GPU algorithm: per hash it generates a **random program** (integer + double-precision floating point with varying rounding modes, branches) and runs it in a virtual machine against a 2 GB dataset with unpredictable access patterns. That needs branch prediction, out-of-order execution, large caches, and AES — exactly what CPUs have and GPUs lack. GPUs run thousands of simple cores executing the *same* instruction in lockstep; divergent branches and random memory access destroy that model. Evidence: the best GPU result in the RandomX CUDA benchmark, an **RTX 2080 Ti, managed ~1,641 H/s at 242 W (6.8 H/W)** versus a desktop CPU at ~100 H/W; an RTX 4090 gets only ~2–4 kH/s at 300–450 W. WebGPU adds nothing that fixes this — compute shaders still cannot do RandomX's floating-point rounding modes, huge-page dataset access, or JIT random-code execution, and they add sandbox overhead. **WebGPU is useful only for a different question: GPU-friendly algorithms (KawPow, Autolykos, Etchash), which are a desktop-GPU matter, not a browser-miner matter.**

### 4.3 Economics — the honest math

Inputs (October–November 2026 snapshots, all sourced): network hashrate ~6.4–6.9 GH/s, block reward ~0.61 XMR (0.6 tail emission + fees), 720 blocks/day = ~432 XMR/day shared network-wide, XMR ~$496–$598. Formula: `XMR/day = your H/s ÷ network H/s × 432`. That is **~0.000063–0.00007 XMR per kH/s per day ≈ $0.031–$0.036/day per kH/s**.

| Worker | Gross/day | Electricity cost/day* | Net |
|---|---|---|---|
| Laptop browser, 200 H/s | ~$0.008 | ~$0.10–0.14 (30–60 W extra) | **≈ −$0.10 to −$0.13/day** |
| 32-thread desktop browser, 850 H/s | ~$0.036 | ~$0.15–0.30 | **≈ −$0.15 to −$0.25/day** |
| Ryzen 7 5800X native, 10–11 kH/s | ~$0.31–0.36 | ~$0.25 (@$0.10/kWh, 105 W) to $0.45 (@$0.18/kWh) | ~breakeven to −$0.09/day |
| Phone native (VoltMiner bench), 420–750 H/s | ~$0.01–0.02 | battery wear + charge cost exceeds it | negative |

\*At US average residential ~$0.18/kWh (Aug 2026); even at $0.10/kWh the laptop browser worker's power costs **~12× its revenue**. Monerica: a browser laptop earns ~$0.008/day and takes **~7 months to reach a 0.003 XMR minimum payout**. With the planned 75/25 split, the user keeps 75% of ~$0.008 = **$0.006/day — ~167 worker-days to earn $1**. MoneroOcean is a profit-switching pool (benchmarks rx/* variants, auto-converts to XMR, 0% pool fee) — but switching cannot fix a 12× cost/revenue gap; on phones it still picks plain Monero (rx/0) as most profitable.

**Verdict: IMPRACTICAL.** Even native desktop CPU mining barely breaks even at average electricity prices; browser mining is 25–80× worse. Any claim that browser mining "earns" users money would be false. It can only be honestly framed as participation/education/demo.

### 4.4 Coinhive history (confirmed)

Coinhive (2017–2019) mined Monero in-browser with **CryptoNight, not RandomX** (RandomX only replaced CryptoNight in November 2019, after Coinhive died). It shut down **8 March 2019**, citing a >50% hashrate drop after a Monero hard fork and an 85% XMR price fall — "isn't economically viable anymore" — plus cryptojacking abuse (62% market share, ~$250k/month at peak per researchers) and browser/AV blocking. Modern web RandomX miners exist but are tiny experiments, not businesses: **VoltMiner Browser Experiment** (WebRandomX + RandomX-bonanza WASM JIT, pthread build, ~2 GB dataset in OPFS, WebSocket→stratum relay to MoneroOcean, 0% fee; October 2026 blog documents a rounding-mode bug that got every share rejected), **SoapBox pool** (browser RandomX + Zephyr, honest "fractions of a cent a day"), **BlackMine** ("a browser thread does a few hashes a second, a desktop XMRig does thousands"). None claims profitability.

### 4.5 What a browser-miner prototype must prove (gates — no claims before these pass)

1. **Measured hashrate in a real browser** (Chrome, Firefox, Safari) on real hardware, fast-mode, multi-threaded — not a synthetic benchmark.
2. **Accepted shares on a real pool** (MoneroOcean or P2Pool) over a sustained run, with rejection rate ~0 — VoltMiner's bug proves local H/s and submit-rate metrics can look perfect while every share is invalid.
3. **Sustained run without throttling** — visible tab vs hidden/background tab; dataset load time and memory on first vs repeat visit.
4. **A real payout received** above the pool minimum, with fee accounting.
5. **Honest cost accounting** — measured extra watts at the wall vs revenue, published next to the hashrate.

## 5. Multi-currency architecture assessment

**Plausibly share one adapter model (same RandomX engine, different parameters):** Monero **XMR (rx/0)**, Wownero **WOW (rx/wow)**, ArQmA **ARQ (rx/arq)**, Zephyr **ZEPH (rx/0)**, Haven **XHV**, Oxen **OXEN**, Salvium **SAL**, Safex **SFX**, Graft, Epic Cash, Tari **XTM** (merge-mineable with XMR), QRL, Etica. ## 6. The 75/25 reward engine — accounting basis (design, not existing code)

Nothing in this section exists yet. This is the recommended accounting basis for the build phase, derived from the master mission's requirements and the existing codebase's patterns (decision audit log, tracked round-trip confirmation, dedupe on natural keys, provenance labelling).

**Accounting basis, explicitly:** distributions are calculated only from **actual confirmed pool rewards** — never from estimated hashrate, never from projected earnings, never from unverified work.

**Recommended model, in order:**
1. Obtain actual confirmed pool rewards (pool API + chain confirmation; the pool's own accounting is the source of truth, cross-checked against the chain where feasible).
2. Deduct explicitly disclosed pool fees and agreed network-related charges (pool fee %, transaction fees for payouts, any agreed infrastructure charge — each disclosed to users before mining, never added silently).
3. Calculate net distributable rewards.
4. Attribute rewards to users using **verified accepted mining shares** (pool-confirmed accepted shares, difficulty-weighted) or an appropriately validated accounting method. A share counts only when the pool accepts it; local hashrate and submit-rate metrics are not evidence of accepted work (VoltMiner's rounding bug proves local metrics can look perfect while every share is invalid).
5. Distribute 75% to participating users, 25% to ATLAS.
6. Record all transactions in an **immutable or tamper-evident accounting ledger** (append-only entries; corrections as reversing entries, never edits or deletes).
7. Provide a complete audit trail (every credit linked to the pool reward batch, the share set, the fee deductions, and the calculation).

**Rules that must hold in the implementation:**
- **Integer atomic units only.** All financial accounting in piconero (1 XMR = 10^12 piconero), never floating-point arithmetic. Rounding rules must be defined in advance (e.g. remainder/dust handling: amounts below the minimum payout stay as pending balance, never silently dropped or rounded to ATLAS).
- **Never calculate payouts solely from estimated hashrate.** Estimates may be shown on the dashboard (labelled ESTIMATE, clearly distinguished from confirmed), but they must never create a payable balance.
- **Never credit unverified mining work.** No credit without pool-accepted shares.
- **Prevent double credits.** Dedupe on the share id (the Mission 1.1 dedupe-on-natural-key pattern) and payout idempotency keys; a reward batch must be processed exactly once.
- **The 75% user share is inviolable.** Referral rewards, if introduced, are funded from the disclosed ATLAS 25% share — never by secretly reducing the 75%.
- **Methodology published.** The transparency page must show the calculation methodology and aggregate figures (total output, total user rewards, total ATLAS share, pool fees, total payouts, active contributors) — verified aggregates only, no user-identifying data.

**What the ledger needs (new tables):** a `ledger` table (append-only: entry id, ts, batch id, user id, type [credit/debit/payout/fee/atlas-share], amount in piconero, source reference, running balance) and a `reward_batches` table (pool reward batch, gross, fees, net, split, status). The existing `decisions` table can carry the audit decisions (new `dept` values `rewards`, `payouts`); the existing `events` table can carry new `kind` values. The `metrics` table must not be overloaded with financial data.

## 7. Payout architecture — simulation/testnet first (gate)

Nothing here exists yet, and **no real financial transaction may be activated without explicit user authorization and successful security testing.** That is a hard gate, not a formality.

**Required features (from the master mission):** configurable minimum payout; confirmed balance verification; user-selected receiving address; payout eligibility; transaction submission; transaction ID tracking; network confirmation tracking; payment history; failed transaction handling; duplicate payment protection.

**Recommended architecture:**
- **A dedicated payout service**, separate from the public website and the browser. Wallet-signing credentials and private keys live **outside the public website and browser**, on isolated, non-shared infrastructure, with restricted permissions and auditable transaction authorization. Nothing custodial on the shared VM (no wallet, no keys, no seed material exists there, and none should be created there).
- **Simulation/testnet first.** Start with a simulation mode (and/or Monero testnet/stagenet where feasible) that exercises the full flow — eligibility, submission, tx ID tracking, confirmation tracking, failure handling, duplicate protection — with no real funds. Only after simulation passes and security testing succeeds may real payouts be considered, and only with explicit authorization.
- **Payout flow discipline, copied from Mission 1:** a payout must only report success when the transaction is confirmed on-chain (tracked round-trip with landing confirmation), never on a successful API response alone. Failed payouts must be retried or refunded to the user's balance with a full audit trail, never lost. Duplicate payment protection via idempotency keys (one payout request → at most one transaction).
- **Minimum payout and dust:** the minimum payout must be set above the pool's minimum and above the transaction fee, so payouts are not consumed by fees. Given the browser-mining economics (§4.3), a browser-only user takes ~7 months to reach a 0.003 XMR pool minimum — the payout UI must show this honestly, not imply quick earnings.
- **Treasury design is an open authorization item** (see §10): who holds the keys, multisig or single-signer, audit access, and recovery procedures must be approved by the user before any real payout service is built.

## 9. Key risks and open questions

### 9.1 Key risks

- **Browser mining is uneconomical (§4.3).** Presenting it as a way to earn money would be false and would damage trust. The honest framing (participation/demo) must be built into the UI copy from the start, not added later.
- **This host cannot carry the platform.** Memory 79.47% and rising, swap active, no GPU, 4 shared vCPUs already ~50% loaded, no listening services, no memory to run a backend. Every new daemon or service must live on authorized external infrastructure; the shared VM stays control-plane only. Mining on this host is permanently unauthorized.
- **VM replacement kills processes.** The daemon was down ~5 min after the ~01:00 VM replacement, and restarted again ~01:52 (two restarts in ~1 hour). The 5-minute cron watchdog is the only automatic restore. Any new service needs the same watchdog + recovery documentation, and the platform must tolerate host replacement without losing accounting state (the ledger must live somewhere durable, not only on this VM).
- **Pool polling latency.** MoneroOcean's API took 7.7 s in a single-shot check. Pool polling under load may time out; the coordinator needs timeouts, retries, and fallback pools (SupportXMR, P2Pool) with the same care as the existing endpoint fallbacks.
- **Silent share invalidation.** VoltMiner's rounding-mode bug proves a miner can report healthy hashrate while every share is rejected. Share validation must be end-to-end (pool-accepted shares), never local metrics alone.
- **Cryptojacking reputation and blocking.** Firefox, Brave, and AV tools block mining scripts; the Chrome Web Store bans mining extensions. A browser miner must survive blocklists, and ATLAS must never be associated with covert mining — explicit consent, visible controls, and immediate stop on page exit are non-negotiable.
- **Pool centralization and custody.** MoneroOcean is a profit-switching pool with 0% fee; relying on one pool's accounting for the 75/25 split makes the pool a single point of trust. Cross-check pool figures against chain data where feasible, and keep the ledger independently auditable.
- **RandomX v2 fork.** A hard fork is coming (date TBD); the WASM build must track it or the prototype goes stale on fork day.
- **Multi-coin illiquidity.** Several RandomX altcoins are near-illiquid; a coin with no exchange volume cannot be paid out or valued honestly.
- **Payout custody.** No treasury design exists and none is approved. Real payouts cannot be built until key custody, multisig, audit access, and recovery are designed and authorized.
- **Referral and legal exposure.** A referral program that rewards recruitment alone risks being an illegal pyramid or misleading investment scheme. User agreements, privacy disclosures, and money-transmission / securities considerations need legal review before launch (Quebec/Canada context).
- **Users lose money mining.** At average electricity prices, even native desktop CPU mining barely breaks even and browser mining loses ~$0.10–0.13/day. The platform has a disclosure duty: show each user their net position honestly, and recommend stopping when uneconomical.
- **Tiny amounts and dust.** Browser earnings are ~$0.006/day per user (75% share). Minimum payouts, transaction fees, and dust handling must be defined so users are not left with unpayable balances.
